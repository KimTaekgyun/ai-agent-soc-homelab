# AI 에이전트 기반 1인 SOC 홈랩 (Suricata + ELK + CloudTrail + LLM 트리아지)

가정망 네트워크와 AWS 계정을 하나의 SIEM으로 모아 탐지하고, LLM 에이전트로 L1 분류를 자동화한 개인 SOC다. 분석 계층은 AWS에서 돌고, 같은 계정의 CloudTrail이 SOC 자신의 운영 계정을 감시한다.

**상태: 구축 완료, 운영 유지 중 (2026-10-23 기준)**

| 영역 | 상태 |
|---|---|
| 네트워크 탐지 (Suricata 인라인) | 운영 중. ET Open 튜닝 1회, 자작 룰 2종(평판 아웃바운드 766룰, 긴 DNS 라벨 1룰), ET 룰셋 매일 자동 갱신 |
| 클라우드 탐지 (CloudTrail) | 운영 중. 감사 로그 무력화(StopLogging/DeleteTrail) 15분 주기 탐지, Discord 알림까지 검증 |
| LLM 트리아지 (watcher + Hermes) | 운영 중. 2026-10-20 오라클 클라우드 → AWS EC2 이전, 에이전트 도구 권한 최소화 |
| ATT&CK 커버리지 | 탐지 6개 영역 + 구조적 공백 5개 영역 정리 |

> 이 문서는 "무엇을 만들었나"보다 **왜 그렇게 했고, 무엇을 감수했고, 무엇을 못 하는지**를 중심으로 적었다.

## 3. 설계 결정과 이유

| 결정 | 근거 | 감수한 것 |
|---|---|---|
| 탐지·알림까지만, 차단(IPS)은 안 함 | 인라인 구조라 오탐 하나가 곧 집 인터넷 단절. LLM에 차단 권한을 주면 alert에 심은 지시문으로 조종당할 수 있음 | 실시간 차단 없음 |
| 센서를 NAT 바깥에 둠 | 회선 전체를 한 지점에서 캡처. NAT 뒤에서는 외부 공격자의 실제 출발지를 볼 수 없음 | 집 안 기기 구분 불가, 내부 이동 미관측 |

| LLM 에이전트 도구를 읽기 전용 1묶음으로 | 신뢰할 수 없는 입력을 읽는 에이전트는 최소 권한. 방어선은 프롬프트가 아니라 OS 권한 | 에이전트의 자율 조사 능력을 쓰지 않음 |
| 룰을 끄지 않고 특정 IP만 억제 | 끄면 같은 룰이 잡을 진짜 신호까지 사라짐 | 억제 목록 갱신 필요 |

## 4. 탐지 엔지니어링

### 4-1. ET Open 튜닝 1회차

30일 alert 약 430만 건의 출처를 추적한 결과 99% 가까이가 SOC 자기 구성 요소였다.

- **결정 기준:** ① 무엇이 일으키나 ② 알림까지 가나 저장만 되나 ③ 남길 가치와 비용 ④ 끄면 무엇을 못 보게 되나
- **적용:** Tailscale 중계 서버 88개 IP에 대해서만 룰 4개 억제. 중계 서버가 아닌 곳과의 같은 통신은 계속 탐지
- 상세: [`docs/tuning-decisions.md`](docs/tuning-decisions.md)

### 4-2. 자작 Suricata 룰

후보는 4가지 기준으로 걸렀다: ① ET Open이 못 보는 빈칸인가 ② 우리 환경에서 실제 위협 신호인가 ③ 오탐이 적은가 ④ 안전하게 재현할 수 있나. **외부 TFTP 다운로드 룰은 ET에 이미 켜진 룰(2008117/2008118)이 있어 기각**했다.

#### 룰 1. 집에서 평판 나쁜 IP로 나가는 연결 (ET 명단 383개 → 766룰 자동 생성)

- **빈칸:** ET 평판 룰(Spamhaus DROP, Dshield, CINS, COMPROMISED)은 `[명단] → $HOME_NET` 방향만 본다
- **룰 형태 (rev 1):**
  ```
  alert ip $HOME_NET any -> [ET 명단] any (msg:"LOCAL Outbound to IP listed in <ET 원래 이름>";
    flow:to_server; threshold: type limit, track by_dst, count 1, seconds 3600;
    classtype:bad-unknown; sid:<변환 SID>; rev:1;)
  ```
- **설계 근거:**
  - `flow:to_server`: 헤더 방향만으로는 "집이 먼저 접속"과 "외부 스캔에 대한 응답"을 구분할 수 없다
  - `track by_dst`: 센서가 NAT 바깥이라 출발지는 항상 하나 → 출발지 기준 제한은 다른 목적지를 숨긴다
  - SID 변환: 평판 −1,400,000 / COMPROMISED −1,300,000. 출처 추적이 되고 다른 자작 룰과 번호가 겹치지 않게
- **운영:** ET 갱신 후 매일 재생성(`scripts/update_rules.sh`, 매일 04:17). 변환 결과가 300개 미만이면 기존 파일을 덮어쓰지 않고 중단, `suricata -T` 문법 검사가 실패하면 재시작하지 않음
- **검증:** RFC 5737 문서용 주소로 양성/음성 테스트, ES까지 도달, 로드 수 계산값과 일치(52,595 / 갱신 후 53,498). 실제 악성 IP 대상 시험은 안전상 하지 않음
- **첫 실전 alert와 개선 (rev 2):** 운영 첫날 1건이 울렸다. 조사해 보니 같은 순간 그 IP가 집으로 GRE 패킷을 보냈고, 공유기가 ICMP 오류로 자동 응답한 것이었다(오탐). Suricata는 GRE와 그에 대한 ICMP 응답을 한 연결로 묶지 못해, 응답을 "집이 시작한 연결"로 봤다. 설계 때 "재현하지 못함"으로 적어둔 한계가 실전에서 드러난 것이다
  - 수정: 명단마다 룰 2개로 분리. ICMP 외 통신은 `flow:to_server; ip_proto:!1`, ICMP는 ping 요청(`itype:8`)만. ICMP 오류(도달 불가 등)는 항상 다른 패킷에 대한 응답이라 제외해도 놓치는 것이 없다
  - 로드 수 53,881(계산값 일치). 같은 유형이 다시 오면 ET 인바운드 룰만 울리고 자작 룰은 조용해야 한다(직접 재현은 불가)
- **한계:** 어느 기기인지 모름. 명단 품질은 ET 갱신에 의존

#### 룰 2. 비정상적으로 긴 DNS 라벨 (DNS 터널링·유출 의심)

- **빈칸:** ET의 DNS 터널링 룰은 특정 도메인 매칭. 길이 기반 범용 룰은 검색 범위에서 없었다
- **기준선(30일):** 전체 이름 길이는 나쁜 기준이었다(70~79자 봉우리 = CloudTrail 버킷 조회, 클라우드 자동 호스트명). **가장 긴 라벨** 기준으로 다시 재니, 50자 이상은 도메인 5개뿐이고 "길고 매번 바뀌는" 모양은 메타 측정용 UUID(fbcdn.net, 492개 고유 이름) 하나였다
- **룰:**
  ```
  alert dns $HOME_NET any -> any any (msg:"LOCAL DNS query with unusually long label (possible tunneling)";
    dns.query; pcre:"/(^|\.)[^.]{50,}\./"; content:!".fbcdn.net"; endswith; content:!".quickconnect.to"; endswith;
    threshold: type limit, track by_src, count 1, seconds 3600; classtype:bad-unknown; sid:1100001; rev:2;)
  ```
- **설계 근거:** 기준 50(40이면 S3 조회 2만 건, 60이면 50~59자 도구를 놓침). 남이 소유한 도메인 예외는 안전(터널링에는 권한 DNS 서버 소유가 필요). 앞의 점은 `evilfbcdn.net` 같은 우회 방지
- **rev 2:** 출발지가 하나라 정상 alert 1건(공유 NAS)이 1시간 제한을 소진해 진짜 신호를 가렸다 → **알려진 정상은 빈도 제한으로 흘리지 말고 예외로**
- **검증:** threshold 없는 테스트 룰로 로직만 검증(45자 0/관측 6, 예외 도메인 0/관측 6·2, 55자 1/관측 4) 후 삭제. 처음 시도한 음성 테스트는 질의가 센서에 도달하지 않아 무효였다 → **음성 테스트는 관측부터 확인**
- **한계:** 평문 DNS만(DoH 불가). 라벨을 짧게 쪼개는 도구는 못 잡음

### 4-3. 클라우드 탐지 (CloudTrail)

#### 룰 1. 감사 로그 무력화 (StopLogging / DeleteTrail, T1562.008)

- **기준선:** 30일간 0건 → 정상 운영에서 울릴 일이 없는 룰
- **구현:** `cloud_watch.py`, cron 15분. 조회 기준은 이벤트 시각이 아니라 **SIEM 도착 시각(`event.ingested`)**: 전달이 늦게 와도 "새로 들어온 것"은 놓치지 않는다. 같은 이벤트는 한 번만 알림. 실패한 시도도 포함
- **검증:** 자기 트레일로 재현 2회. 이벤트 → SIEM 7~10분 → Discord 약 15분. 다시 켜는 StartLogging은 제외됨을 확인
- **한계:** UpdateTrail·이벤트 선택기 변경 같은 우회적 무력화는 미포함. 로그가 꺼진 구간의 활동은 원천적으로 안 보임

**수집 단계에서 얻은 설계 인사이트**
- 글로벌 서비스(IAM 등) 이벤트는 us-east-1에 기록된다
- 같은 필드 값도 주체에 따라 의미가 다르다. 예: 7일간 서비스 74개 조회 299건이 전부 Resource Explorer 서비스 역할 → "다수 서비스 열거" 룰의 첫 오탐 후보를 미리 확인
- CloudTrail은 AWS API 호출만 기록한다

### 4-4. 상관 탐지 규칙 (R-01 ~ R-04)

실제 관측 사례에서 역산한 상관 규칙. 현재는 LLM 트리아지의 판단 기준으로 동작하며 코드 구현은 하지 않았다.

| 규칙 | 조건 | 관측 사례 | 코드 구현 |
|---|---|---|---|
| R-01 다중 포트 열거 | 같은 출발지가 30분 내 서로 다른 서비스 포트 2종 이상 | 있음 | 미구현 |
| R-02 분산 스캔 | 서로 다른 출발지 3개 이상이 1시간 내 같은 포트 | 있음 | 미구현 |
| R-03 평판 → 행위 전환 | 평판 룰 발화 후 같은 출발지에서 내용 기반 룰 발화 | 없음 | 미구현 |
| R-04 침해 응답 + 선행 정찰 | ATTACK_RESPONSE 발화 시 직전 24시간 스캔 이력 | 부분 | 미구현 |

## 5. AI 트리아지

### 구조

- 1층 코드 필터: 평판 룰(SID 범위), 저심각도, 쿨다운
- 2층 LLM: alert를 `<alert_data>` 태그로 격리, MITRE 매핑 출처를 [ET 룰셋 태그] / [운영자 정의] / [추론 기반]으로 구분
- 3층 사람: Discord 리포트로 최종 판단. LLM 출력은 어떤 자동 조치에도 연결하지 않음

### 에이전트 권한 점검

- 트리아지 에이전트(Hermes)에 도구 17묶음이 켜져 있었다: 셸·코드 실행, 예약 작업, 웹·브라우저, 메시지 전송 등
- 필요한 것은 매핑 문서 읽기 하나 → 호출 단위로 `-t skills`만 허용, 호출 횟수 상한
- 스킬 파일은 OS 권한으로 잠금. 수정 지시에 모델은 "권한을 열어주면 된다"고 제안했다 → 방어선은 모델의 판단이 아니라 OS 권한
- 이전 중 발견: 새 버전의 가져오기(import)가 **상시 게이트웨이 서비스를 자동으로 설치·실행**했다. 이전 서버엔 없던 기능이고 `-t skills` 제한이 적용되지 않는 별도 경로라 꺼둠

### 운영하며 드러난 LLM의 한계

- 리포트 안의 집계 숫자가 틀린다 → 건수는 코드가 센 헤더를 기준으로
- 데이터에 없는 값을 채운다 (UDP 공격을 "tcp"로). LLM에는 프로토콜 필드를 보내지 않았기 때문
- **운영자 맥락을 모른다.** 10-20 이전 작업 중 보안그룹이 닫혔는지 확인하려고 새 서버 공인 IP 22번에 접속을 시도한 것이 "Potential SSH Scan OUTBOUND"로 탐지됐다. LLM은 의심도 "높음"을 주고 50분 전의 Realtek 익스플로잇 시도와 시간순으로 엮어 "침해 후 행동 가능성"으로 추론했다. 논리는 그럴듯했지만 두 사건은 무관했다(9월의 testmyids 오판과 같은 구조)
- **이전 판정을 기억하지 못한다.** 같은 익스플로잇 출발지가 여러 실행에 반복 등장해도 매번 새 사건처럼 판정했다
- **같은 룰에 대한 판정이 흔들린다.** 입력 정보 수준이 같은 동일 룰을 실행마다 다른 의심도로 판정한 사례가 있다

**LLM 판정 정확도:** 아직 사람 판정과 체계적으로 비교하지 않았다. 10-12 이후 리포트에서 표본 56건을 뽑아 사람이 먼저 판정하고 LLM 판정과 대조하는 평가를 진행 중이다. 그전까지 이 README의 LLM 관련 주장은 "운영하며 관찰한 것"까지다.

|---|---|---|
| A. 수집기 S3 403 | 권한 부족으로 오판 → 감사 로그로 "서명 없는 요청"임을 찾음 | 실패한 요청의 주체부터 감사 로그로 확인 |
| B. ES 조회 상한 | 6시간 분량 중 67%가 조용히 누락 | 조용한 누락은 "딱 떨어지는 숫자"로 드러난다 |
| C. LLM 전송 상한 | 통과 alert의 59%가 분석 없이 넘어감 | 상한은 "넘치지 않게"가 아니라 "넘치면 알리게" |
| D. Realtek 명령 주입 시도 | alert → flow(응답 0) → 전후 행동 비교 → 자산 확인 순으로 종결 | UDP와 TCP에서 "응답 0"의 무게가 다르다 |
| E. 잊혀진 포트포워딩 3개 | 자산 확인 중 발견 → 봉쇄 → 30일 접근 기록 조사, 침입 흔적 없음 | 설정은 기억이 아니라 화면으로 확인 |
| F. 룰셋 미갱신 | 자작 룰 작업 중 ET 룰이 두 달간 갱신되지 않은 것을 발견 → 단독 갱신, 매일 자동화 | 탐지 품질은 룰을 만드는 것보다 유지하는 데서 갈린다 |
| G. 분석 서버 이전 | 노출 최소화(임시 SSH → Tailscale 확인 → 재부팅 확인 → 인바운드 0 → 양쪽 검증) | 닫았다고 말하지 말고 닫힌 걸 검증 |
| H. 자작 룰 첫 실전 오탐 | 인바운드 GRE에 대한 공유기의 ICMP 오류 응답이 "집이 시작한 연결"로 잡힘 → 엔진 특성 확인 → 룰 분리 | 룰은 배포가 끝이 아니라 시작 |

### 초기 구축 중 디버깅 기록 (2026-08 ~ 09)

| 증상 | 원인 | 해결 |
|---|---|---|
| ET 룰이 전혀 발화하지 않음 | HOME_NET이 내부 대역으로 설정됨. 센서가 NAT 외부에 있어 매칭 불가능 | HOME_NET을 공인 IP로 변경 |
| 대량의 checksum 오탐 | NIC의 checksum offloading으로 캡처 시점 체크섬이 무효로 보임 | Suricata 체크섬 검증 비활성화 |
| 테스트 트래픽이 전혀 탐지 안 됨 | 캡처 인터페이스가 브로드캐스트만 수신 중 (리눅스 브릿지 MAC 학습) | `bridge-ageing 0` 설정 |
| Kibana 검색 0건 (원본에는 존재) | Filebeat 모듈이 필드를 ECS 스키마로 변환(`alert.x` → `suricata.eve.alert.x`) | 실제 인덱스 필드명으로 쿼리 수정 |
| 자동화 스크립트의 alert 수집 실패 | ES 응답 정렬 방향(asc)과 결과 상한이 결합해 최신 alert이 잘림 | 정렬을 desc로 변경 |
| cron에서만 LLM 호출 실패 | cron 환경의 최소 PATH에 실행 파일 경로 없음 | 절대경로로 명시 |
| 필터 통과 alert이 0건 | severity 필드 경로가 ECS로 개명돼 전부 저심각도로 오분류 | `event.severity`로 수정 |
| MITRE 매핑이 전부 "추론 기반" | 스킬의 참조 파일 유실 | 실제 룰 원문 분석 기반으로 재작성 |

## 8. 한계

- **센서 위치:** NAT 바깥이라 집 안 기기를 구분하지 못하고 내부 이동을 보지 못한다
- **탐지 지연:** 네트워크 트리아지 6시간 주기. 클라우드 로그 무력화만 15분
- **LLM 처리 상한:** 한 번에 최대 100쌍. 초과분은 건수만 알린다(누락을 없앤 게 아니라 알리게 만든 것)
- **LLM 정확도 미측정:** 사람 판정과의 비교 평가 진행 중
- **ES 인증 없음:** Tailscale 내부 무인증
- **같은 계정 위험:** 분석 서버와 감시 대상이 같은 AWS 계정. 계정 장악 시 둘 다 무력화 가능
- **운영 의존성:** AWS 크레딧 기간(2027-03) 이후 유료 전환 결정 필요
- **룰 자동 갱신:** 실패는 로그로만 남음(알림 없음). `suricata-update` 자체의 실패는 멈추지 않고 넘어감(이전 룰로 재생성). 문법 검사에서 멈춰도 새 룰 파일은 디스크에 남아 있어, 다음 재시작 때 그대로 로드될 수 있음
- **TLS·페이로드:** 핸드셰이크까지만, 페이로드 미기록
- **TCP 재조립:** 공백 0.59%의 원인 미확정(GRO 병합은 확인)
- **클라우드:** 데이터 이벤트 꺼짐. 감시 대상 워크로드가 적어 시나리오는 재현 기반
- **IDS 버전:** Suricata 6.0.4로 최신 계열이 아님

## 9. 개선 방향

- 운영 작업 기록·환경 사실을 트리아지 참조 문서로 제공(RAG): 운영자 테스트 오판 감소
- 수집 자격증명 유출 탐지(정상 기준선: 집 IP, 정해진 API, 고정 사용자 에이전트)
- 평판 룰을 IP 평판 파일(iprep)로 전환해 로직과 데이터 분리
- 에이전트에 목적별 읽기 전용 도구(ES 조회)를 주어 "조사 후 판단"으로. 전제는 ES 읽기 전용 계정
- 상관 규칙(R-01~R-04) 코드 구현
- 집 쪽에서 분석 서버의 침묵을 감지하는 장치(같은 계정 위험 완화)

## 10. 저장소 구성

- `docs/`: 튜닝 결정표, 사고 기록, ATT&CK 커버리지
- `skills/`: LLM 트리아지 스킬과 MITRE 매핑
- `scripts/`
  - `watcher.py`: 데드맨 스위치 + 1층 코드 필터 + 2층 LLM 트리아지 (현재 운영본, 6시간 주기)
  - `cloud_watch.py`: CloudTrail 로그 무력화 탐지 (현재 운영본, 15분 주기, LLM 없음)
  - `gen_rep_rules.py`: ET 평판 명단을 나가는 방향 룰로 변환 (자작 룰 1)
  - `update_rules.sh`: ET 갱신 → 평판 룰 재생성 → 문법 검사 → 재시작 (CT100, 매일)

- `configs/`: 실제로 고친 설정만 발췌 (suricata, threshold, network, CT100 crontab)
